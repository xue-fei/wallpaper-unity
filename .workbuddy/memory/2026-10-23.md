## 壁纸边缘漏桌面（2px 间隙）修复

**现象**：程序运行后壁纸窗口比屏幕小 2px（实测 1918x1078 vs 真实 1920x1080），右下边缘透出下面的桌面。

**根因**：`WallpaperController.AttachToDesktopCore` 挂接时只做了 `style &= ~WS_POPUP; style |= WS_CHILD;`，
未清除 `WS_CAPTION/WS_THICKFRAME/WS_BORDER/WS_SYSMENU/WS_MINIMIZEBOX/WS_MAXIMIZEBOX` 及扩展边框样式。
Unity 窗口原 `WS_OVERLAPPEDWINDOW` 的 1px 边框保留，客户区比窗口小 2px，沉底后透出桌面。

**修复**（`Assets/Scripts/WallpaperController.cs`）：
1. 挂接时 `&= ~` 掉全部非客户区/边框样式（含 `WS_EX_CLIENTEDGE/WINDOWEDGE/STATICEDGE/DLGMODALFRAME`）。
2. `SetWindowPos` 加 `SWP_FRAMECHANGED` 让样式变更立即重算。
3. 铺满尺寸取自壁纸层 `WorkerW` 的 `GetClientRect`（精确等于桌面覆盖区，单屏多屏都准，保留多屏支持）。
4. 新增 `EnsureClientSize(hwnd, w, h)`：读真实客户区，若偏小按差值补偿窗口外层尺寸，杜绝边缘漏桌面。

注意：铺满目标用父窗口(WorkerW)客户区而非 `Screen.width/height`，可绕开分辨率/DPI 误差。

## 壁纸点击方案：Unity 编译器实测，修复 3 个真实错误

承接 2026-10-22 的 P0–P6 实现。Unity 编译器终于跑起来，报出 3 个真实错误，全部修复。

### 错误 1：CS0266 — `m_Module` 类型声明过窄（`WallpaperInputBridge.cs:239`）

```
error CS0266: Cannot implicitly convert type 'UnityEngine.EventSystems.StandaloneInputModule'
              to 'WallpaperInputModule'. An explicit conversion exists (are you missing a cast?)
```

**根因**：字段声明为 `WallpaperInputModule m_Module;`，但编辑器模式下要把场景原有的
`StandaloneInputModule`（**父类**）对象赋给它 → 父类→子类无法隐式转换。

**修复**：字段类型改为基类 `StandaloneInputModule`。
`inputOverride` 属性定义在基类 `BaseInputModule` 上，本字段唯一的用途就是设它，
因此声明为基类即可满足全部用法。`WallpaperInputModule` 是子类，赋值给基类字段是合法的向上转型。

### 错误 2：CS0246 — `WallpaperController.cs:169` 缺 using

```
error CS0246: The type or namespace name 'EventSystem' could not be found
```
**根因**：该文件有 `using UnityEngine;` 和 `using UnityEngine.UI;`，但**没有** `using UnityEngine.EventSystems;`，
而 `FindObjectOfType<EventSystem>()` 用的是非限定名。
**修复**：补 `using UnityEngine.EventSystems;`。

### 错误 3：CS0173 — 三元表达式类型不兼容（`WallpaperClickReporter.cs:134`）

```
error CS0173: Type of conditional expression cannot be determined because
              there is no implicit conversion between 'UnityEngine.Material' and 'UnityEngine.UI.Graphic'
```
**根因**：写了个 `var target = m_Renderer != null ? m_Renderer.material : (m_Graphic != null ? m_Graphic : null);`
—— `Material` 和 `Graphic` 无隐式转换关系。而且这个 `target` 变量**根本没被使用**
（紧随其后的 if/else if 又重复判断了一遍），属于纯冗余代码。
**修复**：直接删掉 `target`，保留 if/else if 两个分支（两者的赋值目标 `.material.color` vs `.color` 本来就不同，必须分开写）。

### 顺带发现并修复的第 4 个问题（静态检查抓到）

`Editor/WallpaperClickTestMenu.cs:167` 用了**非限定名 `Canvas`**，但该文件没有 `using UnityEngine.UI;`
→ 会报 CS0246。**修复**：改用完整限定名 `UnityEngine.UI.Canvas`（与文件内其他代码风格一致）。

## 建立的静态检查方法（可复用）

编译器报错是「逐个蹦」的，修一个才暴露下一个，效率低。于是写了个 Python 静态检查：

1. **扫描 UGUI 包源码**（`Library/PackageCache/com.unity.ugui@1.0.0/Runtime`，85 个文件）

2. 对待检文件：剔除注释行 → 提取 `using` → 对每个 `UnityEngine.UI.*` / `UnityEngine.EventSystems.*` 类型，
   检查是否满足以下任一条件：
   - 代码里写的是**完整限定名**（如 `UnityEngine.EventSystems.PhysicsRaycaster`）→ 通过
   - 有 `using` 覆盖了它的命名空间 → 通过
   - 否则 → 报缺失

**检查范围**：11 个相关文件（含早期改动的 `NotifyIconItem.cs` / `User32.cs`）

`using UnityEngine;` 能覆盖 `UnityEngine.EventSystems`，**反过来不成立**。
写 C# 文件时 `using UnityEngine;` 必须显式写，不能依赖子命名空间间接覆盖。
`Vector2` / `Vector3` / `Mathf` / `Debug` / `Time` 全在 `UnityEngine` 顶层。

## 第三轮：编译通过，实机跑起来 —— 发现 2 个设计缺陷并修复

### 编译状态
编译已通过（无 CS 错误）。测试场景成功运行，日志显示：
- ✅ UI 生成完成：3 个按钮 + 1 个面板 + 1 个拖拽块
- ✅ 3D 物体生成：红/绿/蓝三个方块 @ z=8.30，viewport x=0.3/0.5/0.7
- ❌ **Bridge 未被装配**：`[Debugger] 未找到 WallpaperInputBridge，模拟点击功能不可用`

### 缺陷 1：测试场景未装配 Bridge（设计缺陷）

**根因**：Bridge 原本只在 `WallpaperController.SetWallPaper()` 里挂载，
而测试场景是**独立新建的场景**（`Tools/壁纸点击测试/生成测试场景` → `EditorSceneManager.NewScene`），
里面根本没有 `WallpaperController`（它挂在 `WallPaper.unity` 的 Main Camera 上）。
→ Bridge 永远不会被装配 → F2/F3 模拟点击完全失效。

**修复**：在 `WallpaperClickTestScene.Start()` 中新增 `BuildBridge()`，
自包含地把 Bridge 装配到场景的 EventSystem 上（已存在则跳过）。
这样测试场景可以独立运行，不需要先跑壁纸流程。

### 缺陷 2：`inputOverride` 的语义我理解错了（重要）

**我上一轮的方案是错的**：用 `!Application.isEditor` 判断，
编辑器模式下「保留原生 StandaloneInputModule + 设 inputOverride = 假输入」。

**查 UGUI 源码 `BaseInputModule.input` getter（第 60 行）**：
```csharp
public BaseInput input {
    get {
        if (m_InputOverride != null)
            return m_InputOverride;      // ← 完全替代！
        ...
    }
}
```
`inputOverride` 是**完全替代，不是叠加**。
一旦设了它，原生模块就再也读不到真实 `Input` ——
所以我那个「两者并存」的方案会让编辑器里的真实鼠标**彻底失效**。

**正确设计：透传（passthrough）**
- **无条件**替换为 `WallpaperInputModule`（覆写 `Process()` 绕过失焦门禁）
- `WallpaperBaseInput` 增加 `m_Injected` 标志：
  - `BeginInjectedFrame()` 置 true（Bridge 在写入假输入前调用）
  - 为 true → 返回假输入状态；为 false → **透传真实 `Input`**
  - `EndFrame()`（LateUpdate）复位

这样两种场景都正确，**无需任何环境判断分支**：
- 编辑器 Play：窗口是正常顶层窗口、能收鼠标 → 无注入点击 → 透传真实输入
- 打包后壁纸：窗口被 SetParent 到 WorkerW、收不到鼠标 → DLL 注入点击 → 假输入生效

### 缺陷 3（顺带）：执行顺序未定义会导致点击延迟一帧

**问题**：`EventSystem` 是 `UIBehaviour`，其 `Update()` → `TickModules()` → `InputModule.Process()`
是 UGUI 读取输入的时机。若 Bridge 的 `Update()` 晚于 EventSystem 执行，
本帧写入的假输入状态会在 EventSystem 读完之后才生效 → **点击延迟一帧甚至丢失**。

**修复**：给 `WallpaperInputBridge` 加 `[DefaultExecutionOrder(-100)]`，
保证它在所有默认脚本（顺序 0）之前运行。

**`LateUpdate` 无需处理**：Unity 生命周期保证 `LateUpdate` 在所有 `Update` 之后，
所以 `EndFrame()` 一定晚于 EventSystem 读取，时序天然正确。

### 验证
- 括号配平：`WallpaperBaseInput {15/15} (16/16)`、`WallpaperInputBridge {72/72} (181/181)`、
  `WallpaperClickTestScene {38/38} (142/142)`、`WallpaperClickDebugger {62/62} (170/170)` ✅
- `m_Module` 声明为 `StandaloneInputModule`，赋值 `AddComponent<WallpaperInputModule>()` 合法（向上转型）✅
- 静态分析（221 个 UGUI 类型）：无新增 using 缺失 ✅

### 关键教训：读源码要读到「语义」层
我上一轮只看到 `inputOverride` 存在、是 public set，就假设它能「叠加」。
实际上必须读 getter 实现才能知道它是**替代**语义。

### 根因（诊断过程）

只有窗口成为壁纸（`SetParent` 到 WorkerW + `HWND_BOTTOM`），

该字段只在 `FixedUpdate` 里用于调试输出，但测试场景没有对应的 Text 对象引用。
若不保护会 `NullReferenceException`。已对两处 `text.text = ...` 加 `if (text != null)`。

### 修复 2：测试场景装配 `WallpaperController`

在 `WallpaperClickTestScene` 新增 `MakeItWallpaper()`，把 `WallpaperController`
挂到测试场景所在 GameObject 上。

**为什么复用而不是重写**：壁纸化涉及 WorkerW 枚举、`SendMessageTimeout(0x052C)`、
Z-Order 调整、分层窗口属性等一堆易错的 Win32 细节，重写等于把 bug 复制一遍。

### 修复 3：Bridge 装配的竞态处理（关键）

**问题**：`WallpaperController.SetWallPaper()` 内部会 `AddComponent<WallpaperInputBridge>()`
（第 173 行）。如果测试场景自己也装一个，就会**重复挂载**。

**时序分析**：
```
Start()
  ├─ MakeItWallpaper()        → 挂上 WallpaperController（其 Start 下一帧执行）
  ├─ StartCoroutine(BuildBridgeDelayed())  → 延迟 0.6 秒
  └─ ...（其他构建）

[下一帧] WallpaperController.Start() → Invoke("SetWallPaper", 0.1f)
[0.1 秒后] SetWallPaper() → SetParent → HWND_BOTTOM → AddComponent<Bridge>
[0.6 秒后] BuildBridgeDelayed 恢复 → BuildBridge() 检查「Bridge 已存在」→ 跳过 ✅
```

所以 `BuildBridge()` 必须**延迟 0.6 秒**执行，避开与 WallpaperController 的竞争。

### 发现但【未修改】的既有 bug（超出本轮范围，已告知用户）

这两处都是**既有代码**（早于本轮点击方案），按「修改范围最小化」原则未改动，

## 壁纸点击方案：静态审查发现 5 个「没成为壁纸」根因（未改代码）

用户报告"打包运行正常，但程序没有成为壁纸"。修复测试场景壁纸化后，
又对壁纸化链路做了完整静态审查，发现 5 个问题（bug 18-22），前 3 个是
"没成为壁纸"的直接嫌疑。

### bug 18 — WorkerW 枚举策略错误（`WallpaperController.cs:221-234`）

```csharp
if (className.ToString() == "WorkerW") { foundWorkerW = hwnd; }
return true;   // 继续枚举 → foundWorkerW 最终指向「最后枚举到的那个」
```

Win10/11 桌面层级下存在**两个 WorkerW**：DefView 之后的（空，壁纸该放这里）
和 DefView 之前的（含桌面图标，放这里会被图标盖住）。当前写法不保证选对。
**正确做法**：回调里找到 `SHELLDLL_DefView` 后，用 `GetWindow(workerW, GW_HWNDNEXT)`
取下一个 WorkerW（RainWallpaper / Lively 的社区验证做法）。

### bug 19 — `SendMessageTimeout` flags 传 0（`WallpaperController.cs:98`）

```csharp
User32.SendMessageTimeout(progman, 0x052C, IntPtr.Zero, IntPtr.Zero, 0, 1000, out _);
```

`fuFlags = 0` 缺 `SMTO_ABORTIFHUNG(0x2)` 等标志。flags=0 时 WorkerW 在某些
系统版本下**不会被创建** → `foundWorkerW == Zero` → 回退 Progman 作父窗口。
日志症状：`未找到 WorkerW，回退使用 Progman 作为父窗口`。

### bug 20 — `GetActiveWindow()` 拿的可能不是 Unity 窗口（`WallpaperController.cs:72`）

```csharp
unityWindow = User32.GetActiveWindow();
```

返回的是**调用线程所拥有且当前有焦点**的窗口。启动瞬间若有启动器 / UAC /
杀软弹窗抢焦点，拿到的就是**错误 HWND**。后果：`SetParent` / `SetWindowPos` /
`SetLayeredWindowAttributes` 全作用在错误窗口上 → 视觉上「Unity 窗口仍是普通
顶层窗口，没成为壁纸」。**正确做法**：`Process.GetCurrentProcess().MainWindowHandle`
（IL2CPP 可用），在窗口创建完成后取。

### bug 21 — DLL 坐标没做屏幕→客户区换算（`native/wallpaper_hook.c:162-194`）

直接用 DefView 客户区坐标除以 Unity 窗口客户区宽高，**无 `ScreenToClient`**。
DefView 与 Unity 窗口客户区原点不同 → 坐标整体偏移。多显示器 / 非 0,0 主显示器
下必然偏移。**影响点击落点精度**（不影响"是否成为壁纸"）。

### bug 22 — DLL 只挂钩 DefView，而 `WM_LBUTTONUP` 不派发给它（`native/wallpaper_hook.c:236-241`）

```c
HWND defView = FindWindowExW(progman, NULL, L"SHELLDLL_DefView", NULL);
SetWindowLongPtrW(defView, GWLP_WNDPROC, (LONG_PTR)HookedDefViewProc);
```

`WM_LBUTTONDOWN` 默认行为设置捕获并返回 → 后续 `WM_LBUTTONUP` 由 `DefWindowProc`
派发给按下时所在窗口，**不进入 DefView 窗口过程** → UP 永远收不到。
且 `SendMessageW` 是同步的，DefView 阻塞会卡 Explorer 线程。
**影响**：注入点击只有 DOWN 没 UP → UGUI 收不到 `ReleasedThisFrame()` → **按钮永不触发**。

### 建议修复顺序

20（句柄来源）→ 19（SMTO flags）→ 18（WorkerW 枚举）→ 22（挂钩目标）→ 21（坐标换算）。
前 3 个修完才能判断"是否成为壁纸"这个前提是否成立。

### 🔑 关键澄清：窗口其实【不需要真的成为壁纸】也能工作

一度以为"必须成为壁纸"是点击功能的前提。读 UGUI 源码后确认**不是**：

- `Process()` 覆写后，失焦门禁已被绕过
- `ProcessMouseEvent()` 内部调 `eventSystem.RaycastAll`，

**所以"没成为壁纸"本身不会让点击失效**。bug 18-22 影响的是另一半：

- 22 → 注入链路（UP 收不到 → 按钮永不触发）

**结论**：「点击没反应」+「无法拖拽」是同一根因 —— DLL 未注入 →
DOWN 从未到达 → `pointerDrag` 恒 null → 拖拽首行就 return。
但拖拽还有**第二个独立根因**（bug 23），即使注入修好也会失效。

### 修复内容

**bug 23（DLL）—— `WM_MOUSEMOVE` 被过滤，拖拽必然失效**
- UGUI `ProcessDrag()` 首行 `if (!pointerEvent.IsPointerMoving() || ...) return;`
- `IsPointerMoving()` = `delta.sqrMagnitude > 0`，`delta = pos - leftData.position`
- 原 `shouldForward = (isDown || isUp || wheelDelta != 0)` 把 MOVE 全过滤掉
  → `Position` 不再变化 → `delta` 恒 0 → **拖拽永不触发**
- 修复：新增 `g_Forwarding` 拖动状态机，MOVE 仅在拖动中转发；
  节流 `MOVE_MIN_INTERVAL_MS = 8`（≈125Hz）；
  用 `wParam & MK_LBUTTON` 自愈；拖动中跳过 `IsOverIcon`；
  **滚轮不得置 `isRealDown`**（否则滚一下滚轮就误入拖动状态）

**bug 24（C#）—— `Update()` 未处理 MOVE**
- 若 MOVE 走 `Press()/Release()` 分支 → `m_Down` 恒 true
  → UGUI 每帧判定 `PressedThisFrame` → **反复触发 `OnPointerDown`**
- 修复：MOVE 提前分流，**只更新 `Position` + `BeginInjectedFrame()`**，
  不碰按键状态；单独记入 `MoveCount`/`LastMove`

**bug 25（C# 防御）—— 拖动期间按键卡死 / 位置跳变**
- `m_HoldInjected`：按住期间保持注入模式，避免某帧无事件时
  透传真实鼠标导致 `delta` 巨大跳变
- `CheckStuckPress()` 看门狗：用 **`GetAsyncKeyState`** 读物理鼠标状态比对
  - 注入=按下、物理=松开 → 丢 UP，`ForceReleaseAll()`
  - **不用「N 帧无事件」判断** —— 拖拽时用户可能停住手不动，
    Windows 不产生 MOVE，按超时会误判并打断正常拖动

**bug 26（DLL 性能）—— 每条消息都写日志**
- 原实现包括 `WM_MOUSEMOVE`，鼠标移动时每秒上千条，
  每条都 `CreateFileW`+`WriteFile`+`CloseHandle`，
  等于在 **Explorer UI 线程**做高频磁盘 I/O → 桌面卡顿
- 修复：MOVE 不记日志

**拖拽落点换算修正**
- `WallpaperClickReporter.OnDrag` 原用 `anchoredPosition += eventData.delta`：
  ① delta 是屏幕像素、anchoredPosition 是画布局部单位，CanvasScaler 下速度错
  ② 逐帧累加会浮点漂移
- 改为世界坐标法：`OnBeginDrag` 记录 `rt.position - worldPoint`，
  `OnDrag` 用 `rt.position = worldPoint + m_DragOffset`
- **为什么不用 `ScreenPointToLocalPointInRectangle`**：
  它返回相对**父物体 pivot** 的坐标，而 `anchoredPosition` 是相对**锚点**，
  两者基准不同，直接相减会算错

## 架构重构：放弃「注入 Explorer DLL」，改用独立伴随进程 + WH_MOUSE_LL

### 根因（为什么之前按钮/拖拽全为 0）

前一版方案把 `WallpaperHook.dll` 注入 Explorer 进程，靠 `WH_GETMESSAGE` 钩子 +
`CreateRemoteThread` 在 Explorer 里跑。实测暴露致命问题：跨会话失效、句柄 PID=0、
`CreateRemoteThread` 退出码被截断 —— 钩子根本没稳定装起来，`OnPointerDown/Up/Click/Drag`
日志计数全为 0。注入 Explorer 这条路从根上就不可靠。

### 新架构（参考 yipiantian native/desktop/main.cpp）

- `native/wallpaper_host.cpp` → 编译 `WallpaperHost.exe`（独立 exe，约 190KB，/MT 静态 CRT）。
- 游戏启动时把自身 `HWND + PID` 当参数传给宿主；宿主负责
  `SetParent` 游戏窗口到 `WorkerW`/`Progman` 桌面层，并在**本进程内**装 `WH_MOUSE_LL`
  系统级钩子（OS 直接回调本进程，无需注入 Explorer）→ 彻底规避跨会话/句柄失效。
- 钩子过滤桌面图标/其他窗口后，把 `POINTER`/`BUTTON`/`LEAVE` 事件经 **stdout 管道**
  转发给 Unity；Unity 经 stdin 回 `RESTORE`/`STOP`/`INTERACT`/`OBSERVE`。
- 坐标约定：宿主把 Y 翻转成「Y 向上」(0=底部)，C# 侧直接乘 `Screen.height` 无需再翻。
- 宿主默认 `interacting=true`（yipiantian 默认 false），壁纸 UI 开箱即用。
- 托盘提示「Unity 壁纸 · 双击返回窗口」；菜单「返回窗口」→`RESTORE`，「退出程序」→`RESTORE`+Quit。

用户「已回退所有代码」，要求**全部用 C# 实现**，壁纸程序 UI 按钮点击正常。
此前任何「注入 Explorer DLL」「独立伴随进程 WallpaperHost.exe（原生 C++）」方案均废弃
（那些是上一轮写的，已被用户回退）。native/ 目录现在只剩 build/，wallpaper_host.cpp 已不在。

### 根因（为何原版按钮点不动）
原 WallpaperController 用 `Input.GetMouseButton`/`Input.mousePosition` 判定点击。
但窗口被 SetParent 到桌面层（WorkerW/Progman，位于图标之下）后，**收不到 WM_MOUSE 消息**
（前台是桌面/Explorer），Unity 的 Input 系统天然读不到 → 按钮恒无响应。
这是所有「Explorer 注入」「原生宿主」方案绕来绕去都没解决的本质问题。

### 新方案（纯 C#，无原生代码、无注入）
核心：在本进程内装 **WH_MOUSE_LL 低层鼠标钩子**（OS 直接回调本进程主线程，无需注入 Explorer），
把桌面上的鼠标事件换算到 Unity 窗口坐标，喂给一个**自定义 UGUI 输入源**。

新增/改写文件（均在 Assets/Scripts）：
- `User32.cs`：增 WH_MOUSE_LL 钩子 API（SetWindowsHookEx/Unhook/CallNextHookEx/GetModuleHandle）、
  MSLLHOOKSTRUCT、RECT、ScreenToClient/GetClientRect/PtInRect/GetWindowRect/GetParent/GetForegroundWindow。
- `WallpaperClickQueue.cs`：线程安全事件队列（Move/Down/Up/Wheel/ForceRelease）。
- `WallpaperBaseInput.cs`：`BaseInput` 子类，暴露假鼠标位置+按键；`mousePresent` 恒 true
  （绕开 StandaloneInputModule 失焦门禁 `!isFocused && !mousePresent → return`）。
- `WallpaperInputModule.cs`：`StandaloneInputModule` 子类，用 WallpaperBaseInput 替换 input，
  每帧 Process 前 Drain 队列、Process 后 EndFrame 清边沿。
- `WallpaperController.cs`（重写）：桌面挂接（保留原 P/Invoke）+ 装 WH_MOUSE_LL + 绑定队列 +
  演示按钮点击计数 + 状态文本 + 托盘恢复/退出。仅 `!UNITY_EDITOR` 走壁纸逻辑（编辑器走真实鼠标，便于调试）。
- `NotifyIconItem.cs`：增 `static Controller`，双击/退出转发到 Controller.RestoreToWindow/QuitApp。

### 关键设计点
- 钩子命中判断：先 `GetForegroundWindow` 看是否桌面(Progman/WorkerW)或本窗口，否则跳过
  （避免在其他程序里操作也误触发壁纸按钮）；再 `PtInRect(窗口屏幕矩形)` + `ScreenToClient` 换算；
  坐标 Y 翻转为「Y 向上」(Unity 约定)。
- 拖拽/按住：`WallpaperBaseInput` 跨帧保持 Held；指针离开窗口或离开桌面时 ForceRelease 防卡键。
- 演示验证：场景已有 Canvas+Button+EventSystem；运行时给 Button 加 onClick 计数，并生成调试文本
  显示「鼠标钩子: 已启用 / 按钮点击次数: N」。

### 编译修复（同日）：POINT 字段大小写 + input 只读
- `User32.POINT` 字段是大写 `X`/`Y`（struct POINT { public int X; public int Y; }），
  控制器换算处误用 `.x`/`.y` → CS1061。已统一改为 `cp.X`/`cp.Y`。
- `StandaloneInputModule.input` 在本 Unity 版本是只读属性（private set），
  `input = m_WallInput` → CS0200。改 `WallpaperInputModule` 用反射写入：
  先 `GetProperty("input").SetValue`（绕过私有 setter），失败再沿继承链写 `m_Input` 字段。

### 修复：壁纸盖住桌面图标
根因：原 `AttachToDesktop` 仅把窗口 `SetParent` 到桌面并在子级 `SetWindowPos(HWND_BOTTOM)`，
但未显式把“桌面图标容器” `SHELLDLL_DefView` 置于最上层；且 `FindDesktopWorkerW` 只查一次，
若 `0x052C` 发出后 WorkerW 尚未就绪就枚举不到 → 回退 `SetParent(Progman)` → 盖住图标。
修复（WallpaperController.AttachToDesktop / FindDesktopWorkerW）：
1. 发送 `0x052C` 后**重试最多 6 次**（每次 sleep 120ms）再枚举，确保 WorkerW 就绪；
2. 新返回 `out defView`（找到即停止枚举）；
3. 挂载后两步 z-order：先 `SetWindowPos(unityWindow, HWND_BOTTOM)` 沉底，
   再 `SetWindowPos(defView, HWND_TOP, SWP_NOSIZE|SWP_NOMOVE|SWP_NOACTIVATE)` 保证图标永远在最上；
4. Progman 兜底路径同样处理 defView（找不到 WorkerW 时）。
新增常量 `HWND_TOP=IntPtr.Zero`、`SWP_NOSIZE`、`SWP_NOMOVE`。

## 修复：图标仍在壁纸之下（Build2026.10.23.16.51.06 Player.log）

### 现象
新日志 `[Wallpaper] 已挂接为桌面壁纸（父窗口=兜底层）` → `isBackground=false` 且走到 **Progman 兜底分支**（`parent=progman`）。
Progman 是老式桌面容器，挂到它上面会盖在 WorkerW 真实桌面之上 → 图标被壁纸遮住。

### 根因
原 `FindDesktopLayer` 只在「找到含 SHELLDLL_DefView 的图标层 WorkerW」后才去取「其后的背景 WorkerW」。
一旦 0x052C 生成的背景 WorkerW 排在图标层之前、或图标层是 Progman 直子 DefView，就一路落到
`IntPtr.Zero` → 退回 Progman → 遮挡图标。而且 0x052C 发完立刻枚举，存在时序竞态。

### 修复
重写 `FindDesktopLayer`：
1. 枚举**所有**顶层 WorkerW，按「是否含 SHELLDLL_DefView」分类：优先取**无 DefView 的背景层**，
   否则取**有 DefView 的图标层**（靠 HWND_BOTTOM 沉到 DefView 之下，图标仍在上）；
   只有完全找不到任何 WorkerW 才退回 Progman（并打 Warning）。
2. 0x052C 循环发送后加 `Thread.Sleep(250)`，等 WorkerW 真正创建，避免时序竞态。
`AttachToDesktop` 把分支描述改成三段（背景WorkerW / 图标层WorkerW / Progman兜底），日志更直观。

### 关键结论
**绝不能把窗口挂到 Progman**（会盖在 WorkerW 桌面之上）。只要总能落到某个 WorkerW，
无论背景层还是图标层，配合 HWND_BOTTOM，图标一定在壁纸之上。

### 按钮不响应的根因（代码审查发现）

**根因 1（高置信度）— `pointerPress` 与 `pointerUpHandler` 解析规则不一致**
Unity 内部：`ProcessMousePress` 里
`pointerEvent.pointerPress = ExecuteEvents.ExecuteHierarchy(currentOverGo, pointerEvent, ExecuteEvents.pointerDownHandler);`
—— **`pointerPress` 取 ExecuteHierarchy 的返回值**（向上找到的第一个 handler，即 Button 本身），
而 `ReleaseMouse` 里 `pointerUpHandler = ExecuteEvents.GetEventHandler(currentOverGo)` 同样向上解析
→ 两者都等于 Button，**一致**。
原代码照抄错了：`ProcessPress` 只调用 ExecuteHierarchy 却把返回值丢掉、直接存 `currentOverGo`
（raycast 命中的**最深层**对象），而 `ProcessRelease` 用 `GetEventHandler(currentOverGo)`（向上找 handler）。
→ 若 raycast 命中 Button 的子物体（如 Text），两者不相等 → **`pointerClickHandler` 永不触发** → 按钮完全没反应。
**修复**：`pointer.pointerPress = ExecuteEvents.ExecuteHierarchy(currentOverGo, pointer, ExecuteEvents.pointerDownHandler);`
（用返回值），兜底 `if (pointer.pointerPress == null) pointer.pointerPress = currentOverGo;`。

**根因 2（中置信度）— 新输入模块未注册进 EventSystem**

把新模块注册进 EventSystem 的模块列表，否则其 `Process()` 根本不会被调用。

## 🎯 根因定案：override Process() 绕过了 raycast（按钮完全没反应的真因）

### 上一轮日志（Build2026.10.23.18.17.47）

### 决定性根因：`Process()` override 绕过了 `GetMousePointerEventData()`
UGUI 的 raycast **原本在 `GetMousePointerEventData()` 里执行**（它内部调 `eventSystem.RaycastAll`），
然后 `ProcessMousePress/Release` 读 `pointerCurrentRaycast`。
而 `WallpaperInputModule` **override 了 `Process()`，完全跳过了 `GetMousePointerEventData()`**
→ `pointerCurrentRaycast` **永远是空的** → 无论点多少次都命中不到任何 UI。
**这就是「按钮完全没反应」的真正根因**（前几轮的 pointerPress/UpdateModules 只是次要因素）。

**修复**：新增 `RaycastAt(PointerEventData)`，在每次 move / press / release / wheel / forceRelease
调用 `ProcessMove` 之前手动 `eventSystem.RaycastAll(p, m_RaycastResults)` 并回填
`p.pointerCurrentRaycast`（取第一个结果，空则 new RaycastResult()）。

### 坐标基准修正（同轮）
- `WallpaperClickQueue.RawClick` 从 `float nx, ny`（归一化）改为 **`int px, py`（客户区像素坐标，Y 向下）**。
- 钩子里 `ScreenToClient` 得到客户区像素后**直接入队**（并 clamp 到客户区范围），
  不再做 `nx = cp.X/client.right` 归一化。
- 输入模块里 `pos = new Vector2(ev.px, ev.py)`，**不再乘 Screen.width/height**。
- **为什么必须这样**：`GraphicRaycaster.Raycast` 源码里

### 根因
- `GraphicRaycaster` 返回的 `m_RaycastResults[0]` 是**最上层**命中对象 = `Text`。
- `Text` 自己不实现 `IPointerClickHandler`，且**不在 Button 的父链上**。
- → `ExecuteEvents.GetEventHandler<IPointerClickHandler>(currentOverGo)` 返回 **null**
- → `pointerPress != pointerUpHandler` → 点击判定永不成立。

### 场景布局（`WallPaper.unity` 实测）
| 节点 | Anchor | AnchoredPosition | SizeDelta | RootOrder |
|---|---|---|---|---|
| `1349739839` (底图) | (0,0)-(1,1) | 0,0 | 0,0 | 0 |
| **`Button`** | (0.5,0.5) | 0,**-137** | **160×30** | 1 |
| `Text` | (0.5,0.5) | 0,0 | **637×129** | 2 |
| `InputField` | (0.5,0.5) | 0,-105 | 160×30 | 3 |

**`Text`(637×129) 远大于 Button(160×30)，且 RootOrder 2 > 1 → 完全遮挡 Button。**
点击的客户区 y 多在 450–900（参考空间 y ≈ -20 ~ -330），而 Button 可点区是
参考空间 y ∈ [112,142]（中心为原点向上为正）→ **用户根本点不到按钮**。

### 修复（3 项）
1. **穿透遮挡查找（`FindClickableTarget`）**：
   遍历 `GraphicRaycaster.RaycastAll` 的**全量列表**（含被遮挡者，按距离近→远排序），
   逐个 `ExecuteEvents.GetEventHandler<IPointerClickHandler>` 向上解析，
   取第一个能响应的对象。`ProcessPress`/`ProcessRelease` 统一用同一套规则
   → 保证 `pointerPress == pointerUpHandler` 成立。
   （`Process()` 已调 `RaycastAt` 填充全量列表，`FindClickableTarget` 直接复用，不重复 raycast。）
2. **演示按钮放大居中**：`SetupDemoUI` 里把 Button 的 RectTransform 设为
   anchor (0.5,0.5)、pos 0,0、`sizeDelta 320×100` → 一眼可见、一点就中。
3. **装饰层关闭 raycast**：新增 `DisableDecorativeRaycast()`，
   把 Canvas 下所有 `Text`/`Image`（排除带 Button 的）的 `raycastTarget = false`，
   让射线穿透到 Button。

### 诊断增强
按下日志新增 `射线列表=Text > Button > …`（最多 6 个 + 总数），
直接暴露「谁在最上层、谁被遮挡」，下次排查遮挡一目了然。

### 判读口诀（更新）
- `命中=Text 点击=0` → 遮挡（现已穿透修复）
- `命中=Button 点击=0` → pointerPress/upHandler 不一致
- `命中=无` → 坐标没落在任何 Graphic 上
