# 2026-11-08 工作日志

## 修复：托盘右键弹出菜单时壁纸盖住桌面图标

### 现象
鼠标在托盘图标上右键，Unity 壁纸窗口会跑到桌面图标之上，把图标盖住。

### 根因（代码链路确认，非推测）
1. `NotifyIconItem.InitWndProc()` 中 `m_HWnd = User32.GetWindow(Application.productName)`，
   即 **Unity 主窗口本身** —— 它已被 `SetParent` 挂到 Progman 下，是 `WS_CHILD` 子窗口，
   靠 z 序插在 `SHELLDLL_DefView`（图标层）之下才能显示图标。
2. `CreateNotifyIconMenu()` 为让菜单「点空白处自动收起」调用 `SetForegroundWindow(m_HWnd)`
   （原注释也强调不能省略）。该 API 会激活目标窗口并把它提到父窗口子链最顶端
   → 壁纸跑到图标层之上，图标被盖住。
   （窗口虽设了 `WS_EX_NOACTIVATE`，但挡不住显式 `SetForegroundWindow`。）
3. 紧接着 `TrackPopupMenuEx` 进入**模态消息循环**，接管 Unity 主线程，`Update()` 完全停摆。
   而 `Update()` 里那套「每 5 秒 z 序再断言」是唯一能把它压回去的代码 →
   菜单显示期间无法自愈，菜单关闭后最坏还要再等 5 秒才轮到校正。

### 修复（仅改 2 个文件，不做其他改动）
`Assets/Scripts/HardCode/Wallpaper/WallpaperController.cs`
- 把 `Update()` 中内联的 (b) z 序再断言抽成
  `public void EnsureZOrderBelowIcons(bool log = true)`：
  - 每次重新 `FindWindowEx(GetParent(), "SHELLDLL_DefView")`（图标层会被重建，缓存句柄会失效）
  - `GW_HWNDPREV` 取上方相邻窗口，不等于图标层才
    `SetWindowPos(..., NOMOVE|NOSIZE|NOACTIVATE)` 压回
  - `unityWindow==0` / `parent==0`（已恢复普通窗口）/ `defView==0`（桌面重建中）直接返回
  - 日志前缀改 `[ZOrder]`；`log=false` 供非主线程/高频调用
- `Update()` 的 (b) 段改为调用该方法；同时删掉 (a) 段前重复的 defView 查询（改由方法内部做）
- 尺寸校正 (a) 仍用 `SWP_NOZORDER`，不动 z 序

`Assets/Scripts/HardCode/Wallpaper/NotifyIconItem.cs`
- `CreateNotifyIconMenu()`：
  - `SetForegroundWindow(m_HWnd)` **之后**立即 `Controller.EnsureZOrderBelowIcons()`
  - `TrackPopupMenuEx` + `DestroyMenu` **之后**再调用一次（兜住模态循环期间的提序）

### 关键点
- **保留** `SetForegroundWindow`（菜单行为需要），只在其后压回 z 序。
- 压回用 `SWP_NOACTIVATE`：只改 z 序、不改前台激活状态，两者互不冲突，
  菜单「点空白处自动收起」不受影响。
- 不新建线程、不改 WndProc 归属、不引入独立托盘消息窗口（改动面最小）。

### 校验
- 无残留 `defView` 局部变量引用；大括号平衡（Controller 128/128，NotifyIconItem 32/32）
- `EnsureZOrderBelowIcons` 定义 1 处、调用 3 处（Update + 菜单前后）
- `GetClassNameOf` 为 `private static`，实例方法调用合法
- `git diff --name-only` 仅 2 个文件
- **未**在 Unity 内实际编译（临时 synthcheck 工具已被清理），待打包验证

### 待用户实测
重新打包后：托盘右键弹出菜单期间及关闭后，桌面图标始终可见；菜单点击外部仍能自动收起。
若实测「菜单显示的那一瞬间」仍有短暂遮盖，说明系统在模态循环内持续提序，
下一步可在 WndProc 的菜单消息（`WM_INITMENUPOPUP` / `WM_MENUSELECT`）里做轻量即时校正，
或起一个菜单期的短守护线程持续压回。

## 第二轮修复：托盘右键时「桌面图标一起闪一下」（上一轮修复的副作用）

### 根因
上一轮的「事后压回」策略本身必然产生可见重绘：
`SetForegroundWindow(m_HWnd)` 把壁纸窗口提到图标层之上（第 1 次 z 序变化），
`EnsureZOrderBelowIcons()` 立刻把它压回（第 2 次 z 序变化）。
Explorer 的 `SHELLDLL_DefView` / `SysListView32` 每次 z 序变化都整片重绘
→ 所有图标同时闪一下。**补丁式压回打不干净，必须从源头不让壁纸窗口被激活。**

### 根治方案：托盘菜单改用独立宿主窗口（Windows 托盘程序标准做法）
菜单全程不碰壁纸窗口 → 它的 z 序一次都不变 → 图标既不盖住也不闪。

`Assets/Scripts/HardCode/Wallpaper/User32.cs`
- 新增 P/Invoke：`CreateWindowEx`（Unicode）、`DefWindowProc`
- 已有可用：`SetLayeredWindowAttributes`、`DestroyWindow`、`SetWindowLongPtr(HandleRef,...)`
  `CallWindowProc`、`GetModuleHandle`（kernel32）、`WndProcDelegate`、`WM_COMMAND`

`Assets/Scripts/HardCode/Wallpaper/NotifyIconItem.cs`
- 新增 `CreateMenuHost()`：用系统预定义 `"Static"` 类（省去 RegisterClass）创建
  `WS_POPUP|WS_VISIBLE` + `WS_EX_TOOLWINDOW|WS_EX_LAYERED` 的 1x1 窗口，
  位置 (-100,-100)，`SetLayeredWindowAttributes(alpha=0)` 全透明、不进任务栏
- 新增 `MenuHostWndProc()`：仅把 `WM_COMMAND` 转发给原 `WndProc(m_HWnd, ...)`，
  复用「关于/显示/隐藏/退出」逻辑；其余交给 `CallWindowProc` / `DefWindowProc`
- 新增 `DestroyMenuHost()`：恢复原 WndProc → `DestroyWindow` → 清空静态引用
- `m_MenuHostProc` 静态持有委托防 GC；`Init()` 创建、`Dispose()` 销毁
- `CreateNotifyIconMenu()`：`host = m_MenuHost != 0 ? m_MenuHost : m_HWnd`，
  `SetForegroundWindow(host)` 与 `TrackPopupMenuEx(..., hwnd: host, ...)` 都指向宿主；
  **删掉激活后的那次压回**（闪烁主因），菜单关闭后保留一次
  `EnsureZOrderBelowIcons(false)` 兜底（正常路径内部 `above==defView` 直接 return，
  不触发 `SetWindowPos`，无重绘）

`WallpaperController.cs`：仅同步 Update 内注释措辞；`EnsureZOrderBelowIcons()` 保留，
Update 的 5 秒周期校正仍兜底其他扰动。

### 副作用（已知，标准托盘菜单行为）
右键菜单期间前台窗口变为 1x1 透明宿主窗口，其他应用会短暂失焦；
菜单关闭后不主动归还焦点，用户点桌面图标可能第一次只是交还焦点。
若需消除，可在菜单前 `GetForegroundWindow()` 保存、菜单后 `SetForegroundWindow` 恢复
（但恢复焦点本身可能触发图标重绘，暂不加）。

### 校验
- `GetModuleHandle` 确认指向 kernel32.dll；`CreateWindowEx` 用 CharSet.Unicode → CreateWindowExW
- 大括号平衡：NotifyIconItem 40/40、User32 17/17、WallpaperController 128/128
- `EnsureZOrderBelowIcons` 调用点：Update 1 处 + 菜单关闭后 1 处
- `git diff --name-only` 3 个文件（新增 User32.cs 的 2 个 P/Invoke）
- **未**在 Unity 内实际编译，待打包验证

### 待用户实测
重新打包后：托盘右键菜单期间及关闭后图标完全不闪、不被盖住；
菜单点外部仍能自动收起；四个菜单项（关于/显示/隐藏/退出）行为不变。

## 第三轮修复：托盘选「退出」时先覆盖图标 + 卡约 1 秒（用户选「核心+广播超时」）

### 诊断（退出链路时间线）
点「退出」→ `WM_COMMAND`（**仍在 TrackPopupMenuEx 模态循环内**）→ `MenuHostWndProc`
转发 → `NotifyIconItem.WndProc` 的 `case QuitID` → `Controller.QuitApp()`：
1. `QuitApp()` 调 `RestoreToWindow()` → `SetParent(NULL)` + `SetWindowPos(HWND_TOP)` +
   `ShowWindow(SW_SHOW)` + `SetForegroundWindow` → 壁纸瞬间变成全屏顶层窗口
   **盖住桌面图标**。该方法本意是给「左键双击托盘恢复为普通窗口」用的，退出时完全多余。
2. `m_QuitRequested = true` 后返回菜单循环；菜单关闭、消息泵交还 Unity，
   **下一帧 `Update()`** 才执行 `UninstallMouseHook` + `Dispose` + `OnWallpaperStop` +
   `TerminateProcess` → 约 1 秒延迟。模态循环期间 `Update()` 根本不跑。
3. 额外耗时：`DesktopSlideshowGuard.NotifyExplorer()` 用
   `SendMessageTimeout(HWND_BROADCAST, ..., 5000)` 同步广播，退出路径上可能再占一段。

### 关键判断
原注释担心的「在模态循环里退出会卡死」特指 `Application.Quit()`（卡在引擎 shutdown）。
`TerminateProcess` 是内核级立即终止，不依赖 Unity 主循环 / 消息泵，在模态循环里调用安全。
之前把该限制泛化到了所有退出方式，才有了延迟到 Update 的设计。

### 改动
`WallpaperController.cs`
- `QuitApp()` 改为即时退出：`UserRequestedQuit=true` → `UninstallMouseHook()` →
  `DesktopSlideshowGuard.OnWallpaperStop()`（硬终止不触发 OnApplicationQuit，必须手动恢复）→
  `TerminateProcess` → `Environment.Exit(0)` 兜底。
  **删掉** `RestoreToWindow()` 调用（窗口随进程销毁，图标全程可见）；
  **不调** `m_NotifyIconItem.Dispose()`（此刻宿主窗口正是菜单 owner，模态循环里销毁可能卡死菜单）。
  `m_QuitRequested = true` 保留作 TerminateProcess 罕见失败时 Update 的兜底。
- `Update()` 的 `m_QuitRequested` 分支保留，降级为兜底，注释同步。
- `OnApplicationQuit()` 注释同步（不再有 RestoreToWindow 前置）。
- `RestoreToWindow()` 本身不动，仍有 3 处引用：左键双击、Attach 失败回退、编辑器退出路径。

`DesktopSlideshowGuard.cs`
- 新增 `BROADCAST_TIMEOUT_MS = 200`，`NotifyExplorer()` 的 `SendMessageTimeout` 超时
  5000 → 200。注册表值在广播前已写入，Explorer 处理 WM_SETTINGCHANGE 通常 <10ms，
  `SMTO_ABORTIFHUNG` 跳过挂起窗口，短超时不影响结果但让退出不再被同步广播拖住。

### 校验
- `RestoreToWindow` 未变成死代码（grep 3 处引用）
- 大括号平衡：Controller 128/128、SlideshowGuard 25/25
- `git diff --name-only` 4 个文件（含前两轮的累积改动）
- **未**在 Unity 内实际编译，待打包验证

### 待用户实测
重新打包后：点「退出」进程立即消失、桌面图标全程可见、无覆盖无卡顿；
系统桌面背景类型仍被正确恢复（注册表 `BackgroundType` 与退出前一致）。
